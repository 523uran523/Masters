# Reading — Development Lessons & Playbook

Этот файл — обобщённые выводы по разработке «Чтения» (Flutter, local‑first трекер книг) и **шаблонный план действий** для ускорения следующих приложений.

> Работаем только в папке `Reading`. Без Git; тесты пока не пишем. Цель — рабочий набросок с ключевыми механиками, локальным хранением и iOS‑подобным Cupertino‑стилем.

---

## 1. Итог проекта

- **Версия:** 0.1.0‑sketch, релизный APK ~61.5 МБ (Android, API 36).
- **Анализатор:** `flutter analyze` чистый.
- **Архитектура:** Provider + sqflite (FFI для десктопа) + shared_preferences; данные только на устройстве.
- **Экраны:** библиотека (4 полки + архив/избранное/коллекции), карточка книги, сессии с таймером, импорт (Goodreads CSV, список, EPUB/FB2, сканер штрихкодов), итоги года, статистика (тренды, календарь), настройки, goal‑sheet, year recap, виджет Android.

Реализовано много mechanical-фич, но часть items (iOS‑виджет, accessibility‑полировка, keyboard shortcuts, пользовательские полки, виджеты) — отложены из-за нативной сложности. Это нормально: набросок проверяет механики, а полировка идёт отдельными спринтами.

## 2. Архитектурные решения, которые сработали

1. **Single source of truth** (`ReadingStore` в Provider) — все экраны читают синхронно, изменения централизованы.
2. **Local-first**: SQLite как durability store + in-memory mirror; бэкап — файл, который выбирает пользователь.
3. **Миграции БД через `onUpgrade`** (v1→v9): добавление колонок (`tags`, `archived`, `audio_chapters`, `cover_color`, `cover_image_path`, `custom_shelf`, `favorite`, `reread_count`, `dnf_reason`, `dnf_at`) без потери данных.
4. **Модели с `copyWith` через sentinel `_unset`** — чистые обновления без null-несчастий.
5. **Импорт с дедупликацией по `bookKey`** (ISBN или title+author) — избегает дублей.
6. **Generate cover в UI** (без сетевых картинок) — работает офлайн и выглядит как Apple.
7. **Разделение engine/UI**: экраны вызывают store, store вызывает репозитории.

## 3. Pitfalls и уроки (дорого обошлись)

1. **Ручная правка скобок/отступов** в сложных UI-деревьях ломает сборку. Лучше использовать `dart format` и анализатор на каждом шаге.
2. **Слишком большие single-файлы** (library_screen, stats_screen, settings) → ошибки каскадом. Лучше дробить на виджеты и файлы.
3. **Смешивание engine и UI в одном файле** (`reading_store.dart` + UI-экраны) замедляет чтение и отладку.
4. **Потеря фокуса на баланс скобок** при вставке обёрток (Semantics, Shortcuts, Dismissible) → сначала надеть обёртку, потом запустить `flutter analyze`, а не накапливать правки.
5. **Нative‑зависимости (home_widget, flutter_local_notifications)** добавляют desugaring/gradle сложность — проверять сборку Android после каждого pub add.
6. **Отложенные пункты (iOS widgets, accessibility‑полировка, keyboard shortcuts) должны помечаться отдельно** и не собираться в «основной» релиз, иначе блокируют поставку.
7. **Сканер/камера** требует permissions в AndroidManifest и права на рантайме; на эмуляторе работает, но необходима проверка на реальном устройстве.
8. **Дубликаты импортов и отсутствующие `show*` хелперы** (ui.dart) вызывают каскадные ошибки — всегда импортировать единый набор helpers.

## 4. Рекомендуемый стек для будущих приложений

- **State:** Provider (простота) или Riverpod (масштабирование/compile‑safe).
- **Storage:** sqflite + sqflite_common_ffi; shared_preferences для настроек; path_provider; isar/hive для no‑sql.
- **UI:** Cupertino (iOS‑стиль) или Material 3; go_router для навигации; reusable widget‑библиотека.
- **Импорт/экспорт:** csv, file_picker, archive, xml; open_file/open_filex.
- **Сетевой поиск:** http + dio; кэширование через sqflite.
- **Сканеры:** mobile_scanner.
- **Уведомления:** flutter_local_notifications (с desugaring).
- **Безопасность:** crypto, local_auth, encrypt (для шифрования файлов).
- **Виджеты:** home_widget (Android) + WidgetKit (iOS, требует Xcode).
- **Доступность:** Semantics, textScaler, контраст, haptics (HapticFeedback).

**Local-first по умолчанию**: нет аккаунта, сервера, рекламы. Бэкап — файл, который выбирает пользователь. Это снижает риски и ускоряет запуск.

## 5. Шаблонный план действий (ускоренный)

### Фаза 0 — Подготовка (0.5 дня)

- [ ] Тема и палитра (AppColorsContext extension).

### Фаза 1 — Движок (1–2 дня)

- [ ] Store (ChangeNotifier) с CRUD и импортом.

### Фаза 3 — Фичи (2–4 дня)
- [ ] Импорт данных (CSV, текст, внешние API).

## 6. Do / Don't

**Do**
- Запускать `flutter analyze` после **каждой** значимой правки.
- Делать маленькие, проверяемые коммиты/шаги (без Git — просто сохранять стабильные состояния).
- Вводить фичи за итерацию «один экран + один репозиторий».
- Держать engine и UI раздельно.
- Добавлять миграции БД сразу (`onUpgrade`), а не откладывать.
- Проверять сборку Android после добавления нативных плагинов (desugaring, permissions).

**Don't**
- Не накапливать правки скобок/импортов без analyze.
- Не смешивать «новая фича» и «рефакторинг» в одном шаге.
- Не откладывать accessibility до конца — Semantics проще добавлять по мере создания виджетов.
- Не пытаться сделать виджеты/iOS‑расширения на Windows (нет Xcode).

## 7. Checklists

### Перед релизом
- [ ] `flutter analyze` без ошибок/предупреждений (желательно).
- [ ] Полный прогон основных сценариев на эмуляторе/устройстве.
- [ ] Проверка тёмной темы.
- [ ] Проверка бэкапа/восстановления.
- [ ] Проверка прав (камера, уведомления).
- [ ] Сборка APK/AAB/IPA.
- [ ] Версия и changelog в README.

### Перед добавлением нативной фичи
- [ ] Проверить, нужен ли desugaring / новые permissions.
- [ ] Тестировать на реальном устройстве (эмулятор для уведомлений/камеры может отличаться).

### Перед добавлением новой сущности в БД
- [ ] Обновить `onCreate` и `onUpgrade`.
- [ ] Обновить модель (`toMap/fromMap/copyWith`).
- [ ] Добавить репозиторий и методы в Store.
- [ ] Проверить restore/import paths.
