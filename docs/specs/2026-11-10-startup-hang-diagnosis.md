# ТЗ: Диагностика зависания при старте на Android (startup-hang-diagnosis)

Статус: **выдано** (senior)
Дата: 10.11.2026
Пользователь: «приложение мастера… на телефоне не запускается, висит на значке/
стартовом экране».

## Симптом
При запуске Мастеров на телефоне приложение зависает на стартовом
экране (логотип/сплэш) — первый фрейм UI не рисуется. Версия на
устройстве уточняется в работе (`aapt2 dump badging` / «О приложении»):
считается актуальной **0.4.5+28** (последний опубликованный, code 28).

## Путь старта (ревью-кандидаты, lib/main.dart)
1. `AppDatabase.open()` — миграции v1→v25. Подозреваемый №1: **бэкфилл v22**
   (цикл по пакетам 200 строк: обязательства/кредиты/`unit_cost_cents`)
   на РЕАЛЬНОЙ базе — если условие выхода цикла на реальном датасете
   не срабатывает, старт зацикливается. Подозреваемый №2: v25
   (`_createStockLocationsSchema`, `_ensurePurchaseReceiptColumns`)
   — идемпотентность на реальной базе.
2. `store.load()` — загрузка всех таблиц (v25 добавляет 5 новых:
   `locations`, `stock_levels`, `stock_batches`, `transfers`,
   `transfer_lines`) + `rebuildLevels`-аналог.
3. `sync.refreshPending()` — считается только если включён meaxis-sync;
   циклы там ограничены `_maxRounds`, но проверить, что нет
   бесконечного ожидания HTTP (таймаут 25 c) перед runApp — важно.
4. `MastersApp` — PIN/биометрия, `_tryServerSync` при старте/resumed.

## Задача
1. **Лог с устройства.**
   - `adb devices` (устройство подключено, `scripts/dev_android.bat`
     знает серийник). Если нет ADB — собрать debug-APK и ставить его
     поверх (данные не чистить), запускать и ловить `flutter`-логи.
   - Лог `adb logcat` после зависания (последние 300+ строк, фильтр
     `Flutter|AndroidRuntime|System.err`) + `app-debug`/`app-release`
     лог `runas`/`logcat -d` — в `docs/specs/logs/` (не коммитить
     лог в git при наличии персданных).
2. **Биссекция по релизам** (если лог не говорит сам):
   - Проверить, на какой версии зависает: 0.4.5+28 (считается),
     при необходимости сверить с 0.3.18+21/0.4.0+22/… через зеркало/
     локальные APK. Кандидаты регрессии: foundation-v22 (бэкфилл),
     Э1–Э5 (схема v22→v25), детальное план-ТЗ `2026-11-07`.
3. **Причина → исправление.**
   - Если зацикливание бэкфилла: починить условие выхода/инкремент
     (не переписывать миграцию задним числом — бэкфилл должен
     остаться идемпотентным для уже «доехавших» БД).
   - Если падение: `Flutter`-исключение в `runApp` → поймать в лог,
     поставить защиту (catch + `migrationHalted`-экран уже есть для
     БД — для старт-ошибок аналогично).
   - Если hang на `await` до `runApp`: вынести тяжёлое в `unawaited`
     (как reminders в main.dart) с прогрессом-индикатором на UI.
4. **Проверка на телефоне:** приложение стартует и показывает первый
   экран (Сегодня), данные не потеряны (`integrity_check` +
   проверка, что база открылась той же, что была до зависания).
5. `flutter analyze --no-pub` 0 ошибок; `flutter test` полный
   зелёный (база 246+); добавить регрессионный тест:
   `migration_v22_test`/`migration_upgrade_test` — бэкфилл на
   фикстуре с >200 заказами завершается (т.е. не бесконечный).
6. Коммиты: fix (слои: data/store/app), push origin main
   (`pull --rebase` БЕЗ `--autostash`, чистое дерево).

## Не входит
- Не бампить версию/не собирать релиз в этой задаче (релиз —
  отдельный слаг после фикса).
- Не трогать web (кроме если общая миграция).
- Не менять логику sync без необходимости.

## Критерии приёмки
- Мастер стартует на телефоне на актуальной БД пользователя
  (без потери данных), первый экран через ~1 с.
- Лог с устройства приложено к отчёту (кратко: строки ключевые).
- analyze 0 ошибок, тесты зелёные, регрессионный тест на бэкфилл.
- Отчёт ≤ 25 строк: версия на устройстве, лог (ключевое), причина,
  fix (файлы), analyze/test, хеши коммитов, статус push.

## Риски
- Телефон не подключён / не виден adb → запросить у пользователя
  подключение (эскалация).
- Миграция уже «сломана» на реальной БД (чёрный ход v25 создан,
  но данные повреждены) → сначала бэкап JSON из-под `run-as`
  (`backupData`-экспорт), потом правки.
