# Итоговый подробный план доработок Masters

**Статус:** финализирован на основе ТЗ от 05.11.2026, анализа конкурентов и рыночных данных Казахстана 2026.
**Принцип:** не меняем архитектурные решения ТЗ (§3 П1–П10, §12), а закрываем выявленные пробелы и переставляем приоритеты под реальные боли микробизнеса.

---

## 0. Стратегическая рамка: почему именно так

Рынок Казахстана: **57% бизнеса работает без CRM**, из них 34% отказались от внедрения, потому что «не увидели быстрого эффекта». Bitrix24 и amoCRM — это инструменты продаж, а не исполнения заказов; YCLIENTS — запись, а не производство. Masters занимает пустую нишу: **«заказ → исполнение → честные деньги»** для тех, кто устал от облака и подписок.

**Ключевое преимущество, которое надо защитить любой ценой:** локальная работа, отсутствие обязательной подписки, отложенная выручка (§12.1), шаблоны T1–T10. Всё остальное — вторично.

**Новый критерий успеха (добавить в §1.3 ТЗ):** «Первый заказ создан и закрыт за ≤ 5 минут с момента установки, без чтения документации».

## 1. Критические исправления (внедрить в Э0, до любой новой функциональности)

Это не этапы, а **шлюзы**, без которых Э0 нельзя выпускать.

### 1.1. Автобэкап перед миграцией

**Проблема:** в §11 ТЗ написано «предложить пользователю бэкап перед апгрейдом». Пользователь не нажмёт.

**Решение:** в `_upgradeSchema` перед первой транзакцией v22:
- создать копию файла БД в `getApplicationDocumentsDirectory()/backups/pre_v22_<timestamp>.db`;
- при успехе миграции — пометить бэкап как «мигрированный», удалить через 7 дней;
- при падении миграции — восстановить автоматически, показать `showAppAlert` «Обновление не удалось, данные сохранены, версия прежняя».

**Тест:** `migration_v22_rollback_test` — симулировать ошибку в шаге 6 бэкфилла, проверить, что данные целы и версия осталась 21.

### 1.2. Проверка «оплачено по старым данным» в бэкфилле

**Проблема:** §4.1.g создаёт `obligation` на `price_cents - paidForJob()`. Если в старой базе платёж был `money_transactions` без привязки к заказу, бэкфилл создаст ложный долг.

**Решение:** перед созданием obligation для заказа:
```sql
SELECT COALESCE(SUM(amount_cents), 0) FROM money_transactions 
WHERE kind IN ('sale','income') AND client_id = :jobClientId 
AND created_at BETWEEN :jobCreatedAt AND COALESCE(:jobClosedAt, now)
```
Если эта сумма ≥ `price_cents` — **не создавать obligation**, пометить заказ как `legacy_paid = 1` (новая колонка в `jobs`, nullable, только для миграции).

**Тест:** `migration_v22_legacy_payment_test` — фикстура с заказом и оплатой без привязки, проверить отсутствие obligation.

### 1.3. Типизация `entity_attributes`

**Проблема:** §4.1.e — универсальная таблица без валидации. Пользователь введёт `вес = "полтора кг"` и `вес = 1.5` в разных заказах. Отчёты сломаются.

**Решение:** добавить в v22 таблицу `attribute_types`:
```sql
CREATE TABLE attribute_types (
  key TEXT PRIMARY KEY,
  value_type TEXT NOT NULL DEFAULT 'text', -- text / number / date
  entity_type TEXT NOT NULL,               -- item / job / client
  label TEXT,
  created_at INTEGER NOT NULL
);
```
В UI шита «+ Параметр» (§6.3) — если ключ есть в `attribute_types`, поле ввода соответствует типу. Если ключа нет — предложить создать тип.

**Тест:** `attribute_typing_test` — попытка записать текст в числовой атрибут отклоняется.

### 1.4. `payment_method` в `money_transactions`

**Проблема:** в Казахстане Kaspi — это не «бухгалтерия», это способ приёма денег. Без отметки пользователь ведёт двойной учёт.

**Решение:** в v22 добавить:
```sql
ALTER TABLE money_transactions ADD COLUMN payment_method TEXT; -- cash / kaspi / card / transfer / other
ALTER TABLE obligations ADD COLUMN payment_method TEXT;
```
UI: в шите оплаты (§6.2, п.5) — `ChipButton: Наличные | Kaspi | Карта | Перевод`. Не интеграция, 2 часа работы. Снимает возражение «а как с Kaspi?».

### Э1. `catalog-order-lines` (0.4.1)

**Добавить к §5.2 ТЗ:**

**1. Быстрый заказ («Сегодня» → «+ Заказ»)**

**3. Проактивный сигнал низкой маржи**
- В `recalcJobTotals` при переходе в `done`: если `margin / price < 0.1` → показать `Pill('низкая маржа', orange)` и `ChipButton('Пересмотреть цены в каталоге')` → открывает `CatalogScreen` с фильтром по этой позиции.

**Тест:** `quick_order_test` — создание заказа в 3 действия; `job_margin_warning_test` — сигнал появляется при марже < 10%.

### Э8. `owner-analytics` (0.4.6) — **сдвинут раньше**

**Почему раньше:** аналитика нужна владельцу для решения «работает ли бизнес», а не мастеру. Она не блокирует операционную работу, но её наличие — критерий «взрослости» продукта.

**Добавить к §5.9 ТЗ:**

**Импорт CSV (клиенты + каталог)**
- В настройках → «Данные» → «Импорт».
- **Клиенты:** CSV с колонками `name, phone, note` (опционально `birthday`).
- **Каталог:** CSV с колонками `name, kind (good/service), unit, sell_cents, cost_cents, category`.
- Валидация: пропускать строки без `name` или `phone` (для клиентов) / `name` (для каталога), показывать отчёт «Импортировано N, пропущено M с причинами».
- **Не требует новых таблиц.** Использует существующие `clients` и `inventory_items`.

**Тест:** `csv_import_test` — импорт 10 клиентов, 5 с дублями по телефону (обновить, не дублировать), 2 без телефона (пропустить).

### Э9. `today-aggregator` (0.4.7) — **новый этап**

**Цель:** «Сегодня» отвечает на вопрос «с чего начать день», а не показывает календарь.

**Секции (сверху вниз, только если есть данные):**

1. **Просроченные оплаты** (из Э2): `ListRow('Иванов, торт 15.11', '12 000 ₽ · просрочка 2 дня', trailing: 'Напомнить')`.
2. **К выдаче сегодня** (из Э1): `ListRow('Заказ #123, торт', 'к 18:00', trailing: 'Открыть')`.
3. **Зависшие заявки** (из Э3): `ListRow('Анна, КП отправлено', 'тишина 3 дня', trailing: 'Напомнить')`.
4. **Низкий остаток** (из Э5, если `module_locations`): `ListRow('Мука', 'осталось 2 кг · минимум 5 кг', trailing: 'Заказать')`.
5. **Задания смены** (из Э7, если включено): `ListRow('Круассаны', 'план 200 · сделано 150', trailing: 'Готово')`.

**Важно:** это **агрегатор**, а не новая сущность. Все данные читаются из существующих таблиц. Никаких новых миграций.

**Если секция пуста — она не рисуется.** Никаких «серых заглушек».

**Тест:** `today_aggregator_test` — при наличии просрочки, выдачи и заявки все три секции отображаются; при пустой базе — `EmptyState('На сегодня задач нет')`.

### Э6. `warranty-service` (0.4.8) — **сдвинут после Э9**

**Почему отложен:** гарантия — важная фича, но она не входит в ядро «посчитать деньги». Для микро-бизнеса (соло-мастер, домашнее производство) она не критична. Для цеха — да, но цех с двумя точками — это уже Э5, и он появится раньше.

**Без изменений относительно ТЗ.**

---

### Э7. `team-shifts` (0.4.9) — **сдвинут последним**

**Почему последним:** самый дорогой этап (серверная работа на meaxis-sync, allow-list, тесты RBAC). Для соло-мастера и малого цеха с 2–3 людьми он не нужен. Если аудитория на старте — микробизнес, Э7 можно отложить до появления первых клиентов с командой > 5 человек.

**Без изменений относительно ТЗ.**
