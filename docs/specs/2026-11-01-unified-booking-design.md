# Unified Booking Design Specification

## (а) Цель и Scope
Объединение двух параллельных потоков планирования — «Записей» (Appointments) и «Заказов» (Jobs) — в единый интерфейс управления временем и процессами.
Цель: избавиться от переключения между календарем и канбаном, создав единую точку входа для планирования любой работы.

**Scope:**
- Модель данных: Объединение Appointment и Job под общим интерфейсом Event.
- UI: Единый экран с переключателем «Канбан / Календарь».
- Регистрация: Настройка первичного режима работы (Заказы vs Записи).
- Бизнес-логика: Совмещение временных слотов записей с дедлайнами заказов.

## (б) Модель данных и миграция

### Текущее состояние
- `Appointment`: `startAt`, `endAt`, `status` (scheduled, confirmed, done, cancelled, noShow).
- `Job`: `dueDate`, `status` (nuevo, inProgress, waitingParts, done, closed).

### Целевая модель
Введение базового класса/интерфейса `Event` (или `BookingItem`).

**Поля общего знаменателя:**
- `id`: String
- `clientId`: String
- `objectId`: String?
- `title`: String
- `startTime`: DateTime (для Appointment = `startAt`, для Job = `dueDate` или `startedAt`)
- `endTime`: DateTime? (для Appointment = `endAt`, для Job = `null` или расчетный)
- `kind`: Enum { `appointment`, `job` }
- `status`: String (унифицированный статус или ссылка на родной статус)
- `note`: String?

### Миграция (v18)
Миграция должна быть неразрушающей (non-destructive). 
1. Создание новой таблицы `unified_events` или добавление колонки `kind` в существующие. 
2. **Рекомендуемый путь:** Оставить таблицы `appointments` и `jobs` как есть, но создать `UnifiedEvent` модель-обертку (Wrapper/Adapter) на уровне Store, которая маппит обе таблицы в единый список для UI.
3. Если требуется БД-уровень: Добавить таблицу-индекс `event_index` (`id`, `entity_id`, `entity_type`, `timestamp`), чтобы быстро получать все события на день/неделю без тяжелых JOIN.

## (в) UI/UX: Единый интерфейс

### Основной экран
- **Верхняя панель:** Переключатель (Segmented Control): `Канбан` $\leftrightarrow$ `Календарь`.
- **Кнопка «+»:** Контекстное меню выбора: «Создать запись» или «Создать заказ».

### Режим «Канбан»
- Колонки определяются статусами `JobStatus`.
- Записи (`Appointment`) отображаются в колонках согласно их статусу (например, `scheduled` $\rightarrow$ «Новый/Ожидание»).
- Карточка записи в канбане:
    - Время (HH:mm)
    - Имя клиента
    - Ресурс (кресло/мастер)
    - Статус записи

### Режим «Календарь»
- Сетка (месяц/день), как в текущем `BookingScreen`.
- Точки/индикаторы на датах: разные цвета для Заказов (оранжевый) и Записей (синий/акцент).
- Список событий дня (Day View):
    - **Запись:** Время $\rightarrow$ Клиент $\rightarrow$ Ресурс.
    - **Заказ:** Дедлайн $\rightarrow$ Клиент $\rightarrow$ Статус процесса.

## (г) Регистрация и Онбординг
В `OnboardingScreen` вопрос «Как принимаете клиентов?» расширяется:
- **Варианты:**
    1. «Только заказы (с дедлайнами)» $\rightarrow$ Модуль `booking` скрыт, главная кнопка «Заказ».
    2. «Только записи (календарь)» $\rightarrow$ Модуль `jobs` в упрощенном виде, главная кнопка «Запись».
    3. «И то, и другое (Гибрид)» $\rightarrow$ Полный Unified UI.

Настройка сохраняется в `SettingsController` (`workMode`).

## (д) Архитектура и контракты

### MastersStore
Добавить методы:
- `List<UnifiedEvent> getEventsForRange(DateTime start, DateTime end)`: возвращает объединенный список.
- `Future<void> convertAppointmentToJob(String appointmentId)`: превращение записи в полноценный заказ (создание Job, удаление Appointment).
- `Future<void> convertJobToAppointment(String jobId)`: назначение конкретного времени заказу.

### Модели
- `UnifiedEvent`: Класс-адаптер.
- `UnifiedEventKind`: enum { `appointment`, `job` }.

## (ж) Краевые случаи
1. **Конфликты:** Запись на время, когда мастер занят по другому заказу (если заказ имеет жесткий временной слот).
2. **Связь:** Запись является «пред-заказом». После подтверждения записи она должна иметь возможность стать заказом одним кликом.
3. **Закрытые заказы:** Не должны отображаться в активном календаре/канбане, только в истории.
4. **Повторы:** Рекуррентные записи (если будут добавлены) должны корректно маппиться в `UnifiedEvent`.

## (з) Критерии приёмки
- [ ] Переключение между Канбаном и Календарем происходит без потери фильтрации.
- [ ] В календаре отображаются и записи, и заказы с дедлайнами.
- [ ] В канбане записи распределены по соответствующим колонкам статусов.
- [ ] Настройку в онбординге влияет на видимость разделов.
- [ ] Нет регрессии в расчетах долгов/оплат (так как данные остаются в родных таблицах).

## (и) План тестов
1. **Integration:** Создать 5 записей и 5 заказов на одну неделю $\rightarrow$ Проверить их отображение в обоих видах.
2. **UX:** Проверить drag-and-drop заказа между колонками $\rightarrow$ Убедиться, что запись (если она в канбане) ведет себя согласно своим статусам.
3. **Migration:** Проверить загрузку старых данных (до v18) $\rightarrow$ Убедиться, что они корректно отображаются в Unified UI.
4. **Settings:** Переключить режим в настройках $\rightarrow$ Проверить скрытие/показ элементов интерфейса.

## (к) Риски и зависимости
- **Зависимость:** `settings-config` должен быть завершен, чтобы `UnifiedBookingScreen` знал, какой режим отображать.
- **Риск:** Перегруженность интерфейса (UI Clutter), если событий слишком много. Решение: строгая фильтрация и группировка по дням.
- **Риск:** Производительность при объединении двух больших списков в памяти. Решение: использование `_viewsDirty` и мемоизации в `MastersStore`.
